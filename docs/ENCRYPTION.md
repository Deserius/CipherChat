# Encryption model

CipherRoom uses established browser and transport cryptography. It does not invent algorithms.

## Transport

- HTTPS / WSS for the application and signaling (provided by the host / reverse proxy).
- WebRTC DTLS-SRTP for audio, video, and screen-share media.

## Messaging (application-level, client-side)

| Piece | Algorithm | Where |
| --- | --- | --- |
| Identity | ECDH P-256 key pair | Web Crypto, per browser tab |
| Room key | AES-256-GCM | Generated by the first key-holder |
| Key wrap | ECDH → AES-256-GCM wrap of the raw room key | Sender to each peer |
| Chat | AES-256-GCM, random 12-byte IV | Per message |
| Files | AES-256-GCM over the whole file, then chunked | Per file |

The server sees:

- display names
- participant ids
- public keys
- wrapped keys (cannot unwrap without a private key it does not have)
- ciphertext + IV
- WebRTC signaling blobs

The server does **not** see:

- ECDH private keys
- the room AES key
- message plaintext
- file plaintext

## Honesty

This is genuine client-side encryption for text and files *when every member’s browser is honest and the room key is only wrapped to intended participants*. It is **not** a substitute for:

- device security
- trusting the people you invited
- a reviewed formal protocol (Signal, MLS, etc.)
- protection against a malicious or replaced JavaScript bundle (the classic web-crypto bootstrap problem)

WebRTC media is encrypted by the browser engine. A TURN server, if used, relays already-encrypted packets but can observe IP addresses and timing.

## Key destruction

`RoomCrypto.destroy()` drops keys in the tab. Room destruction on the server drops session tokens. There is no key escrow.
